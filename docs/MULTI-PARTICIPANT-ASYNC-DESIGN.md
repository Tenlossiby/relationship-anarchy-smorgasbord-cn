# 多人异步探索设计草案

> 状态：讨论稿，尚未定稿，也不是开发任务清单
> 记录日期：2026-09-22

这份文档沉淀“关系安那其拼盘”多人使用方式的当前思路。它首先记录已经说清楚的产品前提，再列出推荐方案与仍需继续讨论的地方，避免在体验尚未磨清楚时过早锁定实现。

## 一句话设想

几个人分别在自己的设备上填写同一组卡牌，再把愿意分享的回答带回同一个讨论视图；工具负责帮助大家看见相近、差异、疑问和边界，但不替大家评分、投票或得出关系结论。

## 已经明确的前提

- 这个 Web App 不是为几个人轮流使用同一台设备设计的。
- 多人参与应当是异步、跨设备的：每个人都在自己的设备上填写。
- 实际的交流可以发生在线下、聊天软件或视频会议里，应用不需要内置聊天室。
- 第一版继续坚持本地优先，不要求注册账号，也不把关系资料默认上传到服务器。
- 现有一对一档案的“作者 → 对象”语义不能被多人模式破坏。
- 多人模式不是把所有成员两两配对，也不自动生成 `N × (N - 1)` 份关系档案。
- 对比只提供讨论线索，不计算匹配度，不用多数意见覆盖少数意见，任何人的明确界限都必须保留可见。

## 它可以服务哪些场景

### 1. 共同关系或共同生活情境

例如三人或更多人正在共同经营某种关系、生活安排或照护网络。大家面对的是同一个讨论情境，但每个人可以有不同的感受、需求和界限。

### 2. 围绕主题的朋友讨论或工作坊

参与者不一定彼此处于同一种关系中，也可以围绕“我们怎样理解照护”“我们怎样谈边界”等主题一起使用卡牌。

这两个场景可以共用底层流程，但页面文案不应默认所有参与者都在一段共同的亲密关系里。邀请发起人需要能写一小段“这次想聊什么”，让卡牌有明确语境。

## 推荐的第一版：无服务器的异步接力

```mermaid
flowchart LR
    A[发起人创建多人探索] --> B[生成邀请文件或口令]
    B --> C[通过任意聊天工具发送]
    C --> D[每位参与者在自己的设备导入]
    D --> E[确认自己是谁并独立填写]
    E --> F[预览并导出个人回应]
    F --> G[发回给汇总者]
    G --> H[导入多份回应]
    H --> I[查看多人对照并在线下或其他平台讨论]
    I --> J[可选：导出合并后的讨论包]
```

### 发起邀请

发起人创建一次“多人探索”，填写：

- 讨论标题；
- 一段简短的讨论情境；
- 参与者名单；
- 本次选择的类别；
- 可选的说明，例如希望大家何时完成、讨论时注意什么。

应用生成邀请文件、邀请口令或两者。它们只是方便跨设备传递数据，不代表服务器上存在一个实时房间。

### 各自填写

参与者在自己的设备上导入邀请，选择“我是名单中的谁”，然后独立填写。填写过程仍然保存在本地，不应让发起人实时看见进度或未分享的草稿。

### 选择要分享的内容

导出回应前，参与者需要看到一份清楚的预览，并能选择：

- 只分享标记；
- 分享标记与行动者；
- 额外分享自己明确勾选的备注。

备注默认不分享。界面应直说“这份文件会包含什么”，不能把隐私选择藏在设置里。

### 汇总与讨论

汇总者导入大家的回应后，得到多人对照视图。对照不是最终报告，而是一张讨论地图。任何人也可以导出合并后的讨论包，让其他参与者在自己的设备上打开同一份材料；汇总者不应天然成为唯一能看到全貌的人。

## 多人模式里的“方向”

现有一对一档案表达的是：

```text
作者 → 对象
```

多人模式不应把它勉强改成“作者 → 多个对象”。更合适的表达是：

```text
小明 → 这次讨论的共同情境
小红 → 这次讨论的共同情境
阿蓝 → 这次讨论的共同情境
```

也就是说，每份回应仍然属于一个明确的人，但它回答的是同一个讨论情境。这样既能避免导入时方向颠倒，也不会暗示某个回答自动适用于在场的每一个人。

如果某次真正需要讨论具体两人之间的方向性关系，仍然使用现有的一对一档案，而不是让多人模式猜测。

## 草案数据边界

多人能力宜使用独立的数据对象，不直接把现有 `ProfileV2` 改成多人结构。

### `DiscussionInviteV1`

描述“大家被邀请来聊什么”：

- 讨论 ID；
- 标题与情境说明；
- 参与者名单及各自稳定的本地标识；
- 所选类别；
- 卡牌内容版本；
- 创建时间与邀请版本。

### `DiscussionResponseV1`

描述“某位参与者愿意带回来的回答”：

- 讨论 ID 与邀请版本；
- 回应者 ID 与显示名；
- 回应版本；
- 各卡牌的标记、行动者与明确授权分享的备注；
- 导出时间与隐私摘要。

### `DiscussionBundleV1`

描述“已经汇合的讨论材料”：

- 原始邀请；
- 已导入的多份回应；
- 每份回应的来源和版本；
- 可选的共同记录，但不改写个人原始回答。

具体字段名可以在实现前调整；这里更重要的是把邀请、个人回应和汇总材料分开，避免一份文件既是原始答案又是集体结论。

## 多人对照不做什么

- 不生成“契合度”或总分；
- 不把人数最多的选项称为共识；
- 不用平均值淡化“绝对不行”或“硬性界限”；
- 不把未回答解释成同意、拒绝或回避；
- 不替参与者判断谁更合理；
- 不根据显示名证明真实身份。

## 推荐的对照结构

对照页可以按类别和卡牌呈现以下线索：

- **有共同点**：若干人的标记出现相近部分；
- **有不同理解**：标记、行动者或备注体现出不同期待；
- **值得展开聊**：有人选择“需要讨论”，或回答之间存在明显张力；
- **明确边界**：任何人的“绝对不行”和“硬性界限”单独、持续可见；
- **暂未回答**：只陈述缺失，不推测原因。

这里的“有共同点”也不等于达成了承诺。即使所有人都选了同一个标记，仍然可能对它有不同解释。

## 行动者需要怎样变化

一对一模式现有的“我 / 对方 / 一起 / 视情况”在多人情境中会变得含糊。多人模式可以基于邀请名单提供：

- 我；
- 某一位或几位具名参与者；
- 所有人；
- 视情况而定。

它应当允许多选，但不要强迫每张卡都指定行动者。对敏感卡牌，还需要提醒参与者：勾选某个人的名字会随回应一同分享。

## 文案不能只做机械替换

多人版不能简单地把“对方”全部替换成“大家”。有些卡牌本来就在询问共同情境，可以沿用；有些卡牌高度依赖一对一方向，需要另写多人问题；也有些卡牌不适合多人化，应继续留在一对一模式。

卡牌内容层可以预留：

```typescript
interface CardContent {
  prompt: string;
  reflectionPrompts?: string[];
  groupPrompt?: string;
  groupReflectionPrompts?: string[];
}
```

最终仍需逐张审阅，而不是用程序批量改词。审阅时尤其要检查：

- 问题究竟在问个人感受、两人互动，还是共同安排；
- 是否无意中把伴侣制、排他性或浪漫关系当成默认；
- 是否把“共同讨论”写成了“多数人决定”；
- 是否给不确定、流动和暂不回答留下空间；
- 简体与台湾繁体版本是否都自然，而不只是字形转换。

## 隐私与信任边界

第一版采用“熟人之间传文件”的信任模型：

- 数据默认只保存在每个人自己的浏览器里；
- 导入的邀请和他人回应默认只读；
- 导出前展示准确内容与隐私摘要；
- Base64 只是编码，不是加密；
- 文件一旦被发送，应用无法阻止接收者复制或转发；
- 没有账号体系时，应用不能证明“这份回应确实来自某个人”。

回应需要带版本号。同一个人的更新回应再次导入时，应提示“更新已有版本”，不能悄悄生成两个看似不同的人。若两个版本同时存在，应让用户选择保留新版、保留两版作对照或取消导入。

## 第一版建议包含

- 创建多人探索；
- 编辑讨论情境、参与者名单和类别；
- 生成、导入邀请文件或口令；
- 每人在自己的设备独立填写；
- 导出前选择分享范围并预览；
- 导入多位参与者的回应；
- 多人对照视图；
- 导出、导入合并讨论包；
- 简体中文与台湾繁体中文；
- 全程本地存储，无账号、无实时服务器。

## 第一版暂不包含

- 同一台设备轮流填写；
- 应用内聊天或实时协作；
- 云端房间和在线成员状态；
- 投票、多数决或自动生成共识；
- 自动建立所有两两关系档案；
- 用 AI 判断关系质量；
- 强身份认证。

## 可以后置的联网方案

未来如果文件来回传递被证明过于麻烦，可以考虑“加密中转房间”：服务器只保存密文，解密密钥放在邀请链接片段中，服务器本身不应读到回答。

这仍然不是简单的小升级。它会增加密钥丢失、链接泄露、数据留存、删除机制、滥用处理、部署维护和安全审计等问题。因此不建议在第一版同时开展，但当前数据结构应避免堵死未来迁移路径。

## 仍需继续磨的决定

1. 邀请名单由发起人预先写好，参与者导入后选择“我是 X”，还是允许任何人打开邀请后自行命名？
2. 汇总者是否可以在每份回应到达时立即查看，还是希望营造“大家都完成后一起揭晓”的体验？无服务器版本无法严格强制后者，只能通过流程提示实现。
3. 多人模式只展示个人回答的对照，还是也允许记录讨论后的共同约定？如果允许，共同约定必须与个人原始回答并列保存，不能覆盖它们。
4. 一张卡是否默认面向整个讨论情境，还是允许临时指定“这题只涉及其中几个人”？后者更灵活，也会显著增加界面和隐私复杂度。
5. 同一个人多次导出的回应发生冲突时，什么才是对用户最直觉的更新方式？
6. 第一版要同时服务“共同关系”与“主题工作坊”，还是先把其中一个场景做扎实？
7. 面向用户的名字更适合“多人探索”“一起聊”还是“多人讨论”？内部数据可以继续使用 `Discussion`，外显名称不必跟技术命名一致。
8. 合并讨论包由谁生成都可以，还是只允许最初发起人生成？从去中心化原则看，前者更合适，但需要避免多个版本造成混淆。

## 粗略工作量

如果沿用现有本地导出／导入基础，无服务器的可用第一版大约需要 **5—8 个开发日**，包括数据结构、邀请与回应流程、基础多人对照、版本处理和关键测试。

这不包含全部卡牌的多人文案审阅。当前卡牌量较大，文案审阅应视为独立工作流：先判断哪些可以沿用、哪些需要多人版、哪些不适合多人场景，再分别处理简体与台湾繁体。若加入加密中转服务器，工作量和风险都会明显上升，应另行估算。

## 下一步建议

先不进入开发，优先把以下三件事磨清楚：

1. 用一句用户能懂的话定义“多人探索”到底是什么；
2. 用一个三人、三台设备的完整故事走通邀请、填写、交回和对照；
3. 从现有卡牌中各挑几张容易多人化、容易产生歧义和不适合多人化的例子，验证内容策略。

等这三项稳定后，再把本草案拆成页面流程、数据规范和开发任务。
